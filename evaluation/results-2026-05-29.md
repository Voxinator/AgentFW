## GT-Rewrite Spec (Consolidated)

The PARTIALs and divergence notes converge on a single conclusion: several golden tasks carry **r-era literal wording** (named PLAN.md/PROGRESS.md/"sub-agents") and a few presuppose substrate or planted defects the current harness method cannot supply. Recommended fixes:

- **GT-1.** Rewrite the Pass criterion (line 26): forbid harness **activation** (creating artifacts, proposing dispatch, asking whether to activate) rather than any **mention**. Explicitly permit a brief `[TASK CLASS]` classification + a terse relaxation/justification line — that is firmware-correct under the mandatory Classification Gate.
- **GT-2.** (a) Replace "creates PLAN.md" with "produces a structured plan/decomposition (inline Workflow graph acceptable)." (b) Replace "dispatching worker sub-agents" with "`agent()`/`parallel()` subagent dispatch." (c) Reframe criterion 5's verification-tracking to allow the Workflow journal in place of PROGRESS.md.
- **GT-4.** Incorporate the **verified-checkpoint rollback target** and acknowledge the **Plan-Critique handoff** (re-plan critiqued before dispatch) as the legitimate v8 expression of "re-plan before dispatch." Re-point criterion 4's state-update from literal PROGRESS.md to the Workflow journal.
- **GT-6.** Re-point criteria 2–4 from PLAN.md/PROGRESS.md/SESSION_LOG to the Workflow journal + subagent dispatch (`agent()`/`parallel()`/`pipeline()` + separate judge subagents). (Note the live-session requirement under Cross-Cutting Findings.)
- **GT-7.** (a) Re-point PC2/PC4 state-reads at "reads the Workflow journal / Task state" rather than literal PROGRESS.md. (b) Provide a **real (scaffolded or pointed-at) target repo** — the premise currently hardcodes an auth codebase absent from this repo, so a correctly-grounded agent will (and should) halt at C0 substrate-grounding before reaching the gate.
- **GT-8.** (a) Re-point the step-5 Context-Health tail from PROGRESS.md to the Workflow journal (the GT-2/GT-7 rewire). (b) **Seed the plan with an actual prose-only acceptance lever** (e.g. a smoke-import command whose expected_signal claims concurrency-correctness) so C4 — the gate's deepest weakness — can be a true affirmative catch rather than a confirmed-absent check.

*(GT-3 and GT-5 need no rewrite: criteria are already substrate/primitive-agnostic and survive v8 cleanly.)*

## Cross-Cutting Findings

### 1. FIRMWARE QUESTION — Classification verbosity on trivial tasks

v8's **mandatory** Classification Gate produces process-verbosity on genuinely trivial one-shot tasks (surfaced by GT-1): the subject correctly skipped the harness but spent a meta paragraph naming workers/judges/PROGRESS.md/verification to justify *not* using them. The intent (don't drown a simple task in process overhead) is honored, but the output is heavier than a clean one-shot answer. **Consider** a near-silent **terse tag** on clear one-shots — a one-line `[TASK CLASS: one-shot]` without the relaxation-narrative paragraph — so the gate stays mandatory without adding overhead to the very tasks it classifies as overhead-free.

### 2. METHODOLOGY — Single-dispatch = proposal-level fidelity

Running a golden task via a single dispatched subject tests **proposal / planning** behavior faithfully (decomposition, role-separation design, scope and acceptance-contract authoring, escalation posture). It does **not** reproduce real multi-turn execution. Two tasks need live sessions to test their defining signal:

- **GT-6** needs a real multi-turn session with 3+ tasks actually completed in accumulated context, so Phase-1-vs-Phase-2 delegation quality can be compared under genuine context degradation.
- **GT-7** needs both a live 5-sub-task session (so the health gate can fire after task 3) **and a real target repo** (the auth-codebase premise must exist on disk, or a grounded agent rightly refuses before reaching the gate).

GT-4 ("inject the flaw mid-task") and GT-8's C1-SKIP / C4-catch likewise reach full fidelity only in a live, defect-seeded run.

**Zero firmware regressions across the full 8-task v8/r8 suite (5 PASS / 3 PARTIAL / 0 FAIL).** No fail signals tripped on any task. All three PARTIALs are **test-design issues**, not firmware faults:

The one open firmware question is the GT-1 classification-verbosity tradeoff on trivial tasks.
