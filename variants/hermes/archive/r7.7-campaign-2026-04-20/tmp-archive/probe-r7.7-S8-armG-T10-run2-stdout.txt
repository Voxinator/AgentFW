# Postgres 12 to 16 Zero-Downtime Migration Plan

## 1. Strategy
**Logical Replication**
Given the 80GB active database size, a physical upgrade (pg_upgrade) would require significant downtime. Logical replication allows the target PG16 instance to stay in sync with the source PG12 instance, enabling a near-instantaneous switchover.

## 2. Tooling
- **Native PostgreSQL Logical Replication** (Publication/Subscription model).
- **pg_dump**: For schema-only extraction.
- **pg_stat_replication**: For monitoring lag.

## 3. Sequence of Operations
1. **Provision Target**: Deploy a new PostgreSQL 16 instance with matching configuration (max_replication_slots, max_wal_senders, etc.).
2. **Schema Migration**: Perform a `pg_dump --schema-only` from PG12 and restore it to PG16 to ensure all tables, indexes, and constraints exist before data sync.
3. **Initialize Replication**:
   - On PG12: `CREATE PUBLICATION pg12_pub FOR ALL TABLES;`
   - On PG16: `CREATE SUBSCRIPTION pg16_sub CONNECTION '...' PUBLICATION pg12_pub;`
4. **Catch-up Phase**: Monitor replication lag. Ensure the WAL sender on PG12 is successfully streaming to PG16.
5. **Switchover**:
   - Set PG12 to `read_only` mode to prevent new writes.
   - Monitor `pg_stat_replication` until lag is 0.
   - Update application connection strings (or DNS/Load Balancer) to point to the PG16 endpoint.
   - Verify connectivity and promote PG16 to primary.

## 4. Service Impact
The three dependent services will experience a brief connection reset during the switchover.
- **Service A, B, and C**: Must be configured with connection pooling (e.g., PgBouncer) or retry logic to handle the momentary loss of the primary database.

## 5. Rollback Strategy
- **Pre-Switchover**: Simply drop the subscription on PG16.
- **Post-Switchover (Failure)**: If PG16 fails validation, point the application connection strings back to the PG12 instance (which was kept in read-only mode to prevent data divergence).

## 6. Risk Assessment
- **Replication Lag**: High write volume may cause lag to grow faster than it can be caught up.
- **Primary Keys**: Logical replication requires all tables to have a `REPLICA IDENTITY` (ideally a Primary Key).
- **Schema Drift**: Any DDL changes made to PG12 during the replication phase must be manually applied to PG16.
