# Postgres 12 to 16 Migration Plan (Zero-Downtime)

## 1. Executive Summary
**Strategy:** Logical Replication.
To migrate an 80GB active database from PostgreSQL 12 to 16 with near-zero downtime, we will utilize PostgreSQL's native logical replication. This allows the target PG16 instance to stay synchronized with the PG12 primary in real-time, minimizing the cutover window to a simple connection string update or DNS switch.

## 2. Strategy & Tools
- **Method:** Native PostgreSQL Logical Replication (Publication/Subscription model).
- **Target:** New PostgreSQL 16 instance (provisioned with identical hardware/resource specs).
- **Primary Tools:** `pg_dump` (schema only), `psql`, `logical replication` (built-in).

### Sequence of Operations
1. **Provisioning:** Set up the PG16 target instance.
2. **Schema Initialization:** Export schema from PG12 (no data) and apply to PG16.
3. **Replication Setup:** 
   - Set `wal_level = logical` on PG12.
   - Create a `PUBLICATION` on PG12 covering all required tables.
   - Create a `SUBSCRIPTION` on PG16 to pull data from PG12.
4. **Synchronization:** Monitor replication lag as the 80GB dataset transfers.
5. **Cutover:** 
   - Quiesce application services.
   - Synchronize sequences (manually set `nextval` on PG16).
   - Update connection strings/DNS to point to PG16.
   - Resume application services.

## 3. Dependent Services
The migration must account for the following service dependencies:
1. **Order API:** High-frequency transactional writes; requires immediate cutover to prevent data loss.
2. **Inventory Service:** Critical read/write dependency; must be paused during the sequence sync phase.
3. **Analytics Worker:** Long-running read queries; must be drained or paused to prevent connection spikes during switchover.

## 4. Execution Roadmap

### Phase 1: Pre-flight & Preparation
- [ ] Audit all tables to ensure every table has a **Primary Key** (mandatory for logical replication).
- [ ] Verify all required extensions (e.g., `PostGIS`, `pgcrypto`) are installed on PG16.
- [ ] Perform a full backup of the current PG12 instance.
- [ ] Baseline performance metrics (CPU, IOPS, Latency) on current PG12.

### Phase 2: Infrastructure & Schema Setup
- [ ] Provision PG16 instance.
- [ ] Perform schema-only dump from PG12: `pg_dump -s -h <pg12_host> -U <user> <db> | psql -h <pg16_host> ...`.
- [ ] Validate schema integrity on PG16.

### Phase 3: Data Synchronization
- [ ] Enable `wal_level = logical` on PG12 (requires restart).
- [ ] Create Publication on PG12: `CREATE PUBLICATION migration_pub FOR ALL TABLES;`.
- [ ] Create Subscription on PG16: `CREATE SUBSCRIPTION migration_sub CONNECTION '...' PUBLICATION migration_pub;`.
- [ ] Monitor `pg_stat_replication` and `pg_subscription_rel` to ensure catch-up.

### Phase 4: Cutover (The "Switchover Window")
- [ ] **Stop Services:** Stop Order API, Inventory Service, and Analytics Worker.
- [ ] **Final Sync:** Wait for `pg_stat_replication` lag to reach 0.
- [ ] **Sequence Sync:** Execute script to sync all sequences: `SELECT setval('seq_name', nextval('seq_name'));`.
- [ ] **Redirect:** Update service environment variables/DNS to PG16.
- [ ] **Start Services:** Bring services back online in order (API -> Inventory -> Analytics).

## 5. Rollback Strategy
In the event of a critical failure during or immediately after cutover:
- **Immediate Revert:** If services fail to connect or error out on PG16, immediately point connection strings back to the PG12 instance.
- **Data Integrity Guard:** The PG12 instance will remain in "Read-Only" mode for 2 hours post-cutover. This prevents "split-brain" where new data is written to PG16 but the rollback points to the old PG12.
- **Manual Reconciliation:** If a rollback is required *after* writes have occurred on PG16, a manual data extraction/import from PG16 back to PG12 will be necessary.

## 6. Risk Assessment

| Risk | Impact | Mitigation |
| :--- | :--- | :--- |
| **Replication Lag** | High | Monitor lag closely; perform cutover only when lag is near zero. |
| **Missing Primary Keys** | Critical | Pre-flight audit of all tables. |
| **Sequence Mismatch** | Medium | Explicitly include sequence synchronization in the cutover script. |
| **DDL Changes** | High | Freeze all schema changes (no `ALTER TABLE`) during the migration window. |
| **Connection Spikes** | Medium | Gradual ramp-up of service instances post-cutover. |
