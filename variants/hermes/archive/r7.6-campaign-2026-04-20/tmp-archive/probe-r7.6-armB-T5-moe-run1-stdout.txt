### Root Cause Analysis
The `editTask` function in `src/hooks/useDashboard.ts` performs an optimistic update followed by a server request:

```typescript
const editTask = useCallback(async (id: string, updates: Partial<Task>) => {

  setTasks(prev => prev.map(t => t.id === id ? { ...t, ...updates } : t))
  try {
    // 2. Server request

    // 3. Update with server response
    setTasks(prev => prev.map(t => t.id === id ? updated : t))
    return updated
  } catch (err) {
    // 4. Rollback on failure
    loadData()
    // ...
  }
}, [loadData])
```

**The Race Condition:**
If a user triggers a data refresh (e.g., through a `loadData()` call or an automatic polling mechanism) *after* the optimistic update (Step 1) but *before* the server request (Step 2) completes, the `loadData()` call will fetch the **old** data from the server. This old data will then overwrite the optimistic update in the local state. 

Because the server request is still in flight, the subsequent `setTasks` (Step 3) might eventually resolve, but if the timing is just right, the `loadData` fetch results can "clobber" the UI with stale data, or the component might re-render with the stale fetched data just before the update settles, causing the "flicker" or persistent staleness the user reported.

2. **Guard `loadData` results:** When `loadData` completes, filter out or merge any tasks that are currently in the `pendingUpdateIds` list, ensuring the local state preserves the most "truthful" (even if optimistic) version of the data until the server confirms the change.
