# Postgres 12 to 16 Zero-Downtime Migration Plan

## 1. Executive Summary
This plan outlines the strategy to upgrade the production PostgreSQL instance from version 12 to 16. To ensure zero downtime for the 80GB active database and its three dependent services, we will use **Logical Replication**.

## 2. Migration Strategy: Logical Replication
Unlike a physical upgrade (which requires downtime), logical replication allows the new PG16 instance to run alongside the PG12 instance, synchronizing data in real-time.

### Key Tools
- **Native PostgreSQL Logical Replication**: Primary method for data synchronization.
- **pglogical (Optional)**: If complex schema migrations or advanced conflict resolution are required.
- **Service Discovery/Load Balancer**: To redirect traffic from PG12 to PG16.

## 3. Execution Roadmap

### Phase A: Preparation
1. **Audit Schema**: Ensure all tables have Primary Keys (required for logical replication).
2. **Provision Target**: Deploy a new PostgreSQL 16 instance with equivalent hardware/config.
3. **Schema Sync**: Export schema from PG12 (without data) and apply to PG16.

### Phase B: Data Synchronization
1. **Initialize Publication**: Create a publication on the PG12 source.
2. **Initialize Subscription**: Create a subscription on the PG16 target.
3. **Catch-up**: Monitor replication lag until the PG16 instance is nearly in sync with PG12.

### Phase C: Switchover (The "Cutover")
1. **Stop Writes**: Briefly pause application writes (or set PG12 to read-only).
2. **Final Sync**: Wait for the last WAL logs to apply to PG16.
3. **Redirect Services**: Update connection strings/DNS for the three dependent services to point to the PG16 endpoint.
4. **Resume Writes**: Unpause applications.

## 4. Dependent Services Impact
The following services must be coordinated during the Switchover phase:
1. **Service A (API/Web)**: Requires connection string update/restart.
2. **Service B (Worker/Background Tasks)**: Must be drained to prevent mid-task failures during switchover.
3. **Service C (Analytics/Reporting)**: Can be updated post-cutover.

## 5. Rollback Strategy
If errors occur during switchover or immediately after:
- **Pre-Cutover Failure**: If replication fails to catch up, abort and investigate. PG12 remains the source of truth.
- **Post-Cutover Failure**: 
    1. Point services back to the PG12 instance.
    2. *Note*: Any data written to PG16 during the window will need to be manually reconciled or recovered via WAL if a reverse replication slot was not established.

## 6. Risk Assessment
| Risk | Impact | Mitigation |
| :--- | :--- | :--- |
| Replication Lag | High | Monitor `pg_stat_replication`; perform migration during low-traffic windows. |
| Missing Primary Keys | High | Pre-migration audit script to identify non-PK tables. |
| Connection Spikes | Medium | Use a connection pooler (PgBouncer) to manage transition. |
