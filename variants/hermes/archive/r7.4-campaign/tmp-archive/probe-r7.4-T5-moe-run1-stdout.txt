### Root Cause
The issue is a **race condition** between the data mutation (e.g., sending a message or updating a task) and the subsequent global dashboard refresh.

In `src/hooks/useDashboard.ts`, after a successful API mutation, the code calls `loadData()` to refresh the entire dashboard state via a `GET /api/dashboard` request. Because the backend performs atomic file writes (writing a `.tmp` file and then renaming it), there is a tiny window where the `GET` request hits the server before the OS has fully finalized the file rename or flushed the new data to disk. If the `GET` request arrives in that window, it retrieves the old version of the file, causing the UI to "revert" to stale data.

### The Fix
Instead of relying on a full, heavy, and race-prone `loadData()` refetch, we should implement **Optimistic Updates** or **Targeted State Updates**. 

I have designed a fix that modifies `src/hooks/useDashboard.ts` to update the local React state directly using the object returned by the mutation. This ensures the UI reflects the change immediately and accurately without needing to wait for a full server-side sync of the entire dashboard file.
