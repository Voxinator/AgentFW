### The Root Cause
The `writeQueue` mechanism is intended to prevent concurrent writes from clobbering each other, but it is implemented inconsistently. 

1.  **Non-Atomic Writes for Standard Tasks:** Functions like `addTask`, `updateTask`, and `deleteTask` read the dashboard file, modify the object in memory, and then call `writeDashboard`. **They do not use the `writeQueue`.**
2.  **The Race Condition:** If a user performs a standard action (like `editTask` via `updateTask`) at the same time an automated process (like `appendTaskMessages` or `appendEventMessages`) is running, the following happens:
    *   `updateTask` reads `dashboard.json`.
    *   `appendTaskMessages` (which *is* queued) reads `dashboard.json`.
    *   `updateTask` writes its version (with the task update).
    *   `appendTaskMessages` finishes its work and writes its version (which contains the *old* task state but with the new message).
    *   **Result:** The task update is lost, and the dashboard shows stale data.

This explains why it is intermittent (it only happens when two writes overlap) and why it feels like "stale data" after a save.

### The Fix
I will refactor `server/storage.ts` to ensure **all** state-changing operations on the dashboard use the `writeQueue`.

1.  **Modify `server/storage.ts`**:
    *   Wrap `addTask`, `updateTask`, and `deleteTask` inside the `writeQueue` logic.
    *   Ensure `replaceEvents` is also queued.
2.  **Verify**: I will simulate a concurrent write scenario using a test script to confirm the fix.
