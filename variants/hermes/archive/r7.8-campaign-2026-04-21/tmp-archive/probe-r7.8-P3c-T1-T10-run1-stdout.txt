## 1. Executive Summary
**Objective:** Upgrade the primary database from PostgreSQL 12 to PostgreSQL 16 with zero downtime for the 80GB active database.

## 2. Technical Strategy: Logical Replication
Given the 80GB size and the requirement for zero downtime, we will use **Native Logical Replication** (built into Postgres).

*   **Source (Publisher):** PostgreSQL 12
*   **Target (Subscriber):** PostgreSQL 16
*   **Mechanism:** 
    1. Export schema from PG12.
    2. Import schema to PG16.
    3. Create a `PUBLICATION` on PG12.
    4. Create a `SUBSCRIPTION` on PG16 to pull data and begin continuous synchronization.

## 3. Execution Roadmap

### Phase 1: Preparation (Pre-Flight)
- [ ] **Provision Target:** Spin up a new PostgreSQL 16 instance with optimized parameters (matching or exceeding PG12 resources).
- [ ] **Schema Sync:** Dump only the schema (no data) from PG12 and apply it to PG16.
- [ ] **Identity Check:** Ensure all tables have Primary Keys (required for logical replication to handle updates/deletes).
- [ ] **Dependency Audit:** Verify connection strings and credentials for the 3 dependent services.

### Phase 2: Synchronization (Data Catch-up)
- [ ] **Initialize Publication:** Execute `CREATE PUBLICATION` on PG12.
- [ ] **Initialize Subscription:** Execute `CREATE SUBSCRIPTION` on PG16.
- [ ] **Monitor Lag:** Use `pg_stat_replication` on PG12 and `pg_stat_subscription` on PG16 to monitor replication lag.
- [ ] **Validation:** Perform checksum/row-count comparisons on sample tables to ensure data integrity.

### Phase 3: Switchover (The Cutover)
*This phase targets a < 30-second window of service interruption (connection reset).*
- [ ] **Stop Traffic:** Gracefully stop/pause the 3 dependent services to prevent new writes to PG12.
- [ ] **Final Sync:** Wait for `pg_stat_replication` to show 0 bytes of lag.
- [ ] **Promote Target:** Break the replication link and finalize PG16 as the primary.

- [ ] **Resume Traffic:** Restart the 3 services.

### Phase 4: Post-Migration & Cleanup

- [ ] **Monitoring:** Monitor PG16 performance and error logs for 24 hours.
- [ ] **Decommission:** After 7 days of stability, decommission the PG12 instance.

3. **Post-Switchover Rollback:** If a failure is detected *after* the cutover, we will need to set up "Reverse Logical Replication" (PG16 as Publisher -> PG12 as Subscriber) to avoid data loss, or accept a brief window of manual data reconciliation.
