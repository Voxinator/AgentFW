### Findings
The issue was identified as a **race condition** in the backend data persistence layer (`server/storage.ts`).

* **The Root Cause**: While message appending functions (like `appendTaskMessages`) were correctly using a `writeQueue` to serialize operations, the primary task mutation functions—`addTask`, `updateTask`, and `deleteTask`—were not. 
* **The Failure Scenario**: If a user updated a task (e.g., changing a title) at the same time a message was being appended, both operations would read the same initial state from `dashboard.json`. One operation would finish and write its changes, but the second operation would then write its version of the state (which still contained the *old* title), effectively clobbering the previous update.

### Fix Implemented
I refactored `server/storage.ts` to ensure **all** dashboard mutations are serialized through the `writeQueue`.
