### Root Cause Analysis
In `/media/psf/Projects/chief-of-staff-dashboard/server/storage.ts`, there is an inconsistent application of a write mutex (`writeQueue`). 

While "append" operations (like `appendTaskMessages`) are wrapped in a `writeQueue` promise chain to ensure atomicity, the primary data-modifying functions—`addTask`, `updateTask`, `deleteTask`, and `replaceEvents`—are **not**.

**The Race Condition Scenario:**
1. `updateTask` is called. It reads the current dashboard state from disk.
2. Simultaneously, `appendTaskMessages` is called. It enters the `writeQueue`, reads the *same* state, appends a message, and writes it to disk.
3. `updateTask` completes its modification in memory (using the *old* state it read in step 1) and writes to disk.
4. **Result:** The message appended in step 2 is clobbered and lost. This explains the "intermittent stale data" reported by the user.

### Verification
The existence of `/media/psf/Projects/chief-of-staff-dashboard/server/__tests__/race_condition_test.ts` confirms this was a known risk. The test specifically iterates through concurrent `updateTask` and `appendTaskMessages` calls to check for message count mismatches.

### Proposed Fix
I will refactor `server/storage.ts` to ensure **all** functions that perform a read-modify-write cycle on the dashboard data are executed within the `writeQueue` mutex. This will guarantee that each operation has a consistent view of the data and that writes are strictly sequential.
