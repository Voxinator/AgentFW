## F-1. SQLite session DB regression (filed 2026-04-26)

**Symptom**: `~/.hermes/state.db` `sessions` table stopped accepting writes at **2026-04-25 00:01:01 UTC**. Step-function timing — most recent entry is `20260424_190101_54ec13`; sessions table contains 1092 entries up to that point; **zero recent sessions** (verified by direct query against the db).

**Scope of impact**:

- `hermes chat --resume <id>`: silently fails to load prior conversation history (this is what the r7.11 item-0 probe surfaced; see DESIGN-r7.11-architecture.md §4.A). Resume reads from SessionDB; with SessionDB unwritten, resume gets empty `conversation_history`.
- `hermes chat --continue [name]`: resolves by recency from SessionDB → fails / picks stale results.
- `sessions list`, `session_search`: degraded (only see entries from before the regression).
- **Discord `/resume`**: depends on the same SessionDB; silently failing.
- **Cron jobs that resume state**: any cron/scheduled task using `--resume` or `--continue` is silently running fresh-context instead of continuing prior state. Operationally: workflows expecting accumulated state are running stateless.
- **Any client of `_session_db`**: same failure mode.

**JSON files are unaffected** — `~/.hermes/sessions/session_*.json` continue to write per-run snapshots. They are observability artifacts, not the resume-loading source. 1026 JSON files on disk; only ~1092 of them indexed in SessionDB; recent gap is the regression.

**Root-cause hypothesis (untested)**: something landed around 2026-04-24 19:01–2026-04-25 00:01 that broke the `_flush_messages_to_session_db` write path or the session creation path (`_session_db.create_session` / `_session_db.ensure_session`, cf. `run_agent.py:933+, :1855+`). Step-function timing suggests a specific change rather than gradual degradation. Candidates:

- A schema migration that didn't run cleanly
- A code path that conditionally skips the SessionDB call
- A failure in the SessionDB constructor that leaves `self._session_db = None` but doesn't surface to the user
- An unhandled exception in the `_flush_messages_to_session_db` call site that gets swallowed

**Next steps (when scheduled)**:

1. `git log` on `run_agent.py` and `hermes_cli/main.py` around the 2026-04-24 19:01 → 2026-04-25 00:01 window — bisect for the change that introduced the failure.
2. Check `~/.hermes/logs/agent.log` and `errors.log` for SessionDB-related exceptions during a fresh `hermes chat` invocation.
3. Test `hermes chat -q 'hello'` and inspect whether `_session_db.create_session` is reached (instrument with logging or attach a debugger).
4. Once root-caused, the fix is presumably small (a single broken commit or a missing config flag). If it's a config flag, document it in the canonical config.

**Why NOT blocking r7.11**: r7.11 architecture treats `verified-state.json` as the exclusive cross-session state channel (per the §4.A addendum). The wrapper does not depend on SessionDB. JSON-file artifacts continue to be written. r7.11 build proceeds regardless.

**Why worth fixing**: any operator-facing Hermes feature that relies on `--resume`, `--continue`, or session-DB queries is silently broken right now. Discord `/resume` and any cron continuation jobs are running stateless. Brian's day-to-day Hermes use degrades silently until this lands.

## F-2. Hermes tool-handler return-type triggers `unhashable type: 'slice'` (filed + fixed in r7.11; 2026-04-27)

**Symptom**: `Error during OpenAI-compatible API call #N: unhashable type: 'slice'` fires when a Hermes tool's handler returns a Python `dict` (or any non-string value). The tool's side effects DO run (state files get written), but the API call after the tool result fails, producing a confused parent that escalates or loops.

**Trigger isolated empirically (r7.11 item 6b bisection, ~5-min wall-clock)**: the Hermes tool dispatch path expects handlers to return `str`. When a handler returns a dict, downstream result-handling code (likely a slice-based truncation `result[:N]` cast to a hash key in a cache lookup, given the `unhashable type: 'slice'` shape) fails. The exception bubbles up as a generic `Exception` caught at `run_agent.py:9041`.

**Bisection narrative** (ruled out, in order):
- TOOL_DESCRIPTION length / content: NOT the trigger (V5/V_PURE: 17-char descriptions still error)
- Schema features (additionalProperties, multi-type, defaults, enums): NOT the trigger (V_PURE simplified to single-string-param-only still errors)
- Library imports: NOT the trigger (V_PURE has zero `r7_11_lib` imports)
- Tool name: NOT the trigger (`vp_test` errors same as `verify_phase`)
- Toolset name (`r7_11` vs `delegation`): NOT the trigger (V_TOOLSET still errored)

**Trigger confirmed**: handler return type. A stub returning a string runs cleanly:

```python
def _handle(args, **kw):
    return f"verify_phase ran with goal={args.get('goal')!r}. Status: ok."
```

A stub returning a dict triggers the slice error:

```python
def _handle(args, **kw):
    return {"status": "ok", "received": args.get("goal")}
```

**Fix**: shims must JSON-encode dict results before returning.

```python
def _handle(args, **kw):
    result = verify_phase_tool(...)  # returns dict
    return json.dumps(result)        # return string
```

This pattern is now in the three r7.11 shims (`r7_11_verify_phase.py`, `r7_11_end_session.py`, `r7_11_escalate.py` as emitted by `probe-r7.11-stage.sh`).

**Reference smoke (attempt-3, 2026-04-27 22:55 PT)**: with the fix in place, all three tools dispatch cleanly, no slice errors, sentinel + verified-state.json populated correctly, parent emits coherent final message. Smoke wall-clock: 10s. See `SMOKE-REPORT-r7.11-6b-attempt-3.md`.

**Relationship to F-1**: independent. F-1 is SQLite session-DB regression; F-2 is an upstream Hermes API-layer assumption about handler return types. Existing tools like `delegate_worker` happen to return strings (delegate_task returns dicts that get string-coerced upstream — verify before relying on this assumption for new tools), so they don't trip the trigger.

**Upstream fix candidate**: the dispatch path at `tools/registry.py:dispatch` is typed to return `str` but allows handlers to return any type without coercion. Either (a) coerce non-str returns via `json.dumps` inside `dispatch`, or (b) document the return-type contract loudly in the registry interface and handler examples. Recommended — would prevent this from biting future tool authors. Filing as upstream Hermes work; not blocking r7.11.

**Status**: workaround shipped in r7.11 shims. Upstream contract clarification pending.

### F-2 addendum — operator decision (2026-04-27): post-r7.11 cleanup, NOT pursued in this campaign

Operator decision after the trigger isolation: the upstream `tools/registry.py:dispatch` coercion is a candidate post-r7.11 cleanup but is **NOT pursued during this campaign**. Reasoning:

1. **Scope**: a `dispatch()` modification is a canonical Hermes change outside the `.probe-*` convention. That's a different risk class than r7.11 staging — touches the canonical tool registry that all existing tools depend on, and any change there should be tested against the full tool suite, not just r7.11 tools.
2. **Workaround is sufficient for r7.11**: the explicit `json.dumps(...)` in each shim's `_handle()` is the right scope. Each shim is small and inspection-friendly; the coercion site is visible at the boundary where dict-shaped Python results meet Hermes' string-shaped tool-result wire format.
3. **Don't add isinstance-check fallback to shims**: explicit `json.dumps` at known points is more debuggable than implicit coercion. If a future shim accidentally returns a non-string, we WANT it to surface loudly (slice error → fix the shim) rather than get silently coerced (subtle bug downstream when the model misinterprets the wrapped value).

Recorded for future Hermes maintenance work, not on the r7.11 critical path.

**F-2 still observed in r7.11 item 8 trial 2 (2026-04-28)**: the parser bug fires on `write_plan_md`'s schema (different from the r7.11 shims' schemas). Parent pivots to `write_file` cleanly; format teaching from `write_plan_md`'s tool description still lands pre-call. Identical r7.10 pattern. Cosmetic only (operator gets a noisy but recoverable session). The json.dumps fix doesn't apply to `write_plan_md.py.r7.10-min` because that tool's parser-bug trigger is in its description text/schema shape, not its return value.

## F-4. content_verify.py mishandled absolute paths in PLAN.md (FIXED 2026-04-29)

**Symptom**: PLAN.md authored with absolute paths (e.g., `/tmp/r7.11-item8-scaffold/src/api/export_api.py`) was producing spurious FABRICATION findings. Trial 2's content_verify output had 4 such findings, all phantom.

**Root cause**: the path-resolution code did `scaffold_root / declared_path.lstrip("./")`. Python's `str.lstrip()` strips a CHARACTER SET, not a string prefix — so `"/tmp/foo".lstrip("./")` returned `"tmp/foo"` (not `"/tmp/foo"` as the author probably intended). That stripped path then got joined under scaffold_root, producing a fictional path that could never exist.

**Fix**: added `_resolve_plan_path(scaffold_root, declared_path)` helper at content_verify.py:212. If `Path(declared_path).is_absolute()`: return as-is. Else: join with `scaffold_root / declared_path.lstrip("./")` (the lstrip is harmless for relative paths).

Three call sites patched: `_check_serializers`, `_check_wired_api`, `_check_plan_fabrication`. Plus a defensive `try/except ValueError` around `relative_to(scaffold_root)` in `_check_wired_api` that previously could crash on absolute paths outside scaffold_root.

Tests added: T20 (absolute path that exists → no FAB), T21 (absolute path missing → FAB cites verbatim).

**Verified by**: 21/21 content_verify tests + all 6 prior r7.11 suites still green; spot-check on trial-2 archive: 4 spurious FABs → 2 legitimate FABs (one for `docs/api_docs.md` not written, one for parent's `tests/test_export.py` differing from declared name).

## F-5. Tier-2 import resolution doesn't see scaffold venv (filed 2026-04-29)

**Symptom**: r7.11 item 8 trial 2 (and trial 3 prep) found that `verify_phase` tier-2's import resolution check uses `importlib.util.find_spec(...)`, which resolves against the **running Python's sys.path**. The verifier runs in Hermes' venv (`~/.hermes/hermes-agent/venv`), so it finds packages installed there but NOT packages installed in the scaffold's `.venv` (`<scaffold_root>/.venv/lib/.../site-packages/`).

Empirical confirmation:

```
~/.hermes/hermes-agent/venv/bin/python:
  fastapi:    None       (NOT FOUND — installed only in scaffold venv)
  reportlab:  None       (NOT FOUND — installed only in scaffold venv)
  httpx:      ModuleSpec(...)  (found — happens to be in Hermes venv)
  pytest:     ModuleSpec(...)  (found — happens to be in Hermes venv)
```

**Why it matters**: parents naturally write code against modern Python frameworks (`fastapi`, `pydantic`, third-party DB libraries, etc.). The architecturally clean pattern is per-scaffold venvs (each project carries its own deps). Tier 2 currently can't honor that — it sees only Hermes' venv. Result: workers write correct code; verifier flags it as unresolvable; phase fails verification despite real implementation.

**Three paths forward**:

A. **Surface only; live with the limitation**. Operators install third-party deps in Hermes' venv as a side effect of setting up trials. Workable but pollutes Hermes and breaks the per-scaffold-venv invariant.

B. **Workaround: pip install in Hermes' venv per-trial**. For item 8 trial 3: install fastapi+reportlab in `~/.hermes/hermes-agent/venv` so the verifier sees them. Reversible (`pip uninstall` post-trial). Doesn't fix the architectural gap; gets the trial unblocked.

C. **Architectural fix: extend tier-2 to discover scaffold's `.venv/lib/.../site-packages/`**. Add a `find_spec`-like resolution that searches scaffold's venv first, then falls back to Hermes' venv. ~30-50 LOC + tests. Right long-term answer; correctly bigger than B.

**Status**: pending operator decision. Trial 3 is gated on this. Worth noting: B is the trial 3 unblocker; C is the right answer for item 9 (n=5) and beyond.

**Why NOT blocking r7.11 architecturally**: the wrapper, sentinel, archive, decision tree, escalate path, read-only verified-state.json invariant all worked correctly in trial 2. F-5 is a verifier-implementation gap, not an architectural gap.

### F-5 resolution (2026-04-29) — B1 (PYTHONPATH injection at probe time only)

Operator chose **B1**, a canonical-preserving variant of B: rather than `pip install` into Hermes' venv (which leaves cached metadata + dependency state — not byte-identical, so not a true canonical preservation), inject the scaffold venv's `site-packages` into the subprocess `PYTHONPATH` env var at launch time. Process-scoped only; vanishes when the wrapper exits; Hermes' canonical venv stays untouched.

**Implementation**: `LocalProcessTransport.launch_hermes` in `hermes_multi.py` (lines 498–508). Detects `<scaffold_root>/.venv/`, finds `lib/python*/site-packages/` via glob (no hardcoded minor version), prepends to existing `PYTHONPATH` (no trailing colon when none existed). 11 LOC. Tested via T26 in `test_hermes_multi.py` (3 cases: injection-when-present, no-op-when-absent, prepend-existing).

**Empirical verification** on `/tmp/r7.11-item8-scaffold/.venv/`:

```
Baseline Hermes Python (no PYTHONPATH):
  find_spec("fastapi")    → None
  find_spec("reportlab")  → None

Augmented (PYTHONPATH=<scaffold>/.venv/lib/python3.11/site-packages):
  find_spec("fastapi")    → /tmp/.../fastapi/__init__.py
  find_spec("reportlab")  → /tmp/.../reportlab/__init__.py
  import fastapi          → 0.136.1
  import reportlab        → 4.5.0
```

**F-5 stays open** — B1 is the bridge that lets r7.11 ship; the proper architectural fix (verify-config declares scaffold venv path, OR tier-2 auto-discovers `<scaffold_root>/.venv/`, OR a `find_spec_against_paths` shim that searches scaffold venv first then falls back to Hermes venv) remains r7.12 architecture work. Filing this resolution does not close F-5.

## F-6. Scaffold venv must match Hermes' Python version (filed 2026-04-29)

**Symptom**: B1 PYTHONPATH-injection (F-5 resolution) made `find_spec("fastapi")` resolve from Hermes' Python against the scaffold's `.venv/lib/pythonX.Y/site-packages`. But actual `import fastapi` failed with `ModuleNotFoundError: No module named 'pydantic_core._pydantic_core'` — pydantic_core ships a Python-version-tagged C extension (`_pydantic_core.cpython-312-aarch64-linux-gnu.so`); Hermes runs Python 3.11.15 (uv-managed at `~/.local/share/uv/python/cpython-3.11.15-linux-aarch64-gnu/`); ABI mismatch.

Surfaced empirically during item 8 trial 3 prep when post-B1 verification went one step beyond `find_spec` and called real `import`. The original scaffold venv had been built with the system's `python3.12`; switching to a 3.11-built venv resolved the ABI mismatch.

**Why tier 2 doesn't catch this**: tier 2 uses `importlib.util.find_spec`, which only locates the spec by walking sys.path. It doesn't load the module or trigger any C-extension binding. ABI mismatches surface only at actual import time — which would happen in tier 3.5 (opt-in runtime smoke) or when phase-3 tests execute against the scaffold.

**Workaround for r7.11 (in place)**: scaffold venv at `/tmp/r7.11-item8-scaffold/.venv/` rebuilt 2026-04-29 with Hermes' Python:

```
PY=/home/parallels/.local/share/uv/python/cpython-3.11.15-linux-aarch64-gnu/bin/python3.11
$PY -m venv /tmp/r7.11-item8-scaffold/.venv
/tmp/r7.11-item8-scaffold/.venv/bin/pip install fastapi reportlab httpx pytest
```

Site-packages is now `python3.11/`. Both `find_spec` AND `import` succeed under PYTHONPATH-augmented Hermes Python. Scaffold-build instructions for any future r7.11 trial scaffold need the same discipline: discover the Python version Hermes is running (`~/.hermes/hermes-agent/venv/bin/python --version` or read `pyvenv.cfg.version_info`) and match it.

**Proper r7.12 fix candidates**:

A. **`verify-config.json` declares Python version**: scaffold author declares e.g. `{"python_version": "3.11"}`; wrapper validates that scaffold venv's site-packages path matches at startup; halts with a clear "scaffold venv pythonX.Y doesn't match Hermes' pythonY.Z" message before launching.

B. **Tier 3.5 detects ABI mismatch as a distinct error class**: instead of letting an ABI-mismatch import surface as a generic "ImportError on third-party dep", tier 3.5 introspects the failure (e.g., walk the traceback for `cpython-X-...so` patterns) and emits a specific `corrective_dispatch` directing the operator to rebuild the scaffold venv.

C. **Scaffold-build helper**: ship a `make_scaffold_venv.sh` that always uses `~/.hermes/hermes-agent/venv/bin/python -m venv ...` directly — eliminates the version-discovery step entirely. Cheapest fix.

Recommended: **C as the immediate ergonomic fix** for r7.11+ scaffold builds; **A as the structural fix** for r7.12 (catches drift even if a scaffold author forgets the helper). B is nice-to-have but only fires after the broken state is reached.

**Status**: workaround documented and applied to item-8 scaffold. F-6 stays open as r7.12 candidate work.

**Why this is good catch material**: precisely the integration-real failure mode unit tests can't surface. The B1 unit tests (T26) verify env-var construction shape, not whether any actual import composes downstream. Caught only because post-impl verification went one step beyond `find_spec` to `import`.

## F-8. Parent batches phases instead of handing off between each (filed 2026-04-29; trial 3 — observational)

**Symptom**: r7.11 architecture intent: each phase = one Hermes session; `end_session_for_handoff` between phases; wrapper drives phase loop. Trial 3: parent ran phases 2 + 3 + 4 in one session (798s), only handed off after all 4 phases verified. Wrapper saw all-verified → COMPLETE. Multi-session resumable mechanism only exercised across 1 boundary (phase 1 → phase-2/3/4 batched session), not 3 as designed.

**Allowed by the architecture**: parent decides handoff timing. If the parent has remaining context budget and recognizes the next phase is dispatchable from the current state, batching is more efficient than handoff overhead.

**But**: the architecture's value proposition is "split work across sessions to keep context-window manageable across long horizons." That value isn't being realized when the parent stays in one long session. For T6 (4 small phases) it doesn't matter. For larger horizons it would.

**Open question for operator**:

A. **Wrapper enforces per-phase handoff**: after `verify_phase(phase=N) → passed`, wrapper rejects subsequent `delegate_worker` calls until `end_session_for_handoff` fires. Forces the multi-session pattern. Loses parent autonomy.

B. **Parent autonomy as-is**: accept batching when parent chooses; trust parent's context-budget judgment. Means the multi-session mechanism is opt-in by parent rather than enforced.

C. **Soft nudge**: wrapper logs a warning when parent batches phases; aggregates "batched-phase-count" into trial reports for operator review. Doesn't change runtime behavior.

**Status**: not blocking; observational. Filing for design conversation. Recommended: C for now, revisit after item 9 if batching distorts n=5 results.

## F-11. write_plan_md worked-example uses shell syntax (filed 2026-04-29; trial 4b)

**Symptom**: r7.11 item 8 trial 4b phase 3 escalated with `[ENVIRONMENT:command-not-found: cd]`. Parent's PLAN.md included `Acceptance Command: cd /tmp/r7.11-item8-scaffold && pytest tests/test_export.py` — copied verbatim from `write_plan_md.py.r7.10-min`'s worked-example template. Tier 3.7 launches subprocesses via `shlex.split` + `subprocess.run` (operator's spec — argv-style, no shell injection risk). `shlex.split("cd ... && pytest ...")` yields `["cd", "...", "&&", "pytest", "..."]`; `subprocess.run` raises `FileNotFoundError` because `cd` is a shell builtin, not a binary. Tier 3.7 correctly classified as `[ENVIRONMENT:command-not-found: cd]` (env-failure, not acceptance-failure — the spec's distinction held). Parent revised 3 times trying to investigate the environment (corrective_dispatch's misleading "fix the environment" guidance); max revisions exhausted; wrapper escalated.

**Important context**: this is a TEACHING bug, not an architecture defect. Tier 3.7 mechanism worked exactly as designed. When the same trial's `pytest tests/test_export.py` is run manually post-trial, it exits 0 with 6/6 tests passing. The actual acceptance criterion is satisfied; the verifier just couldn't exercise it because the command shape doesn't match the execution model.

**Root cause**: `write_plan_md.py.r7.10-min`'s tool description worked-example. The `Acceptance Command:` line was added during F-7/F-8 enablement work using shell syntax (`cd ... && pytest ...`) that doesn't compose with the argv-style subprocess execution tier 3.7 was specified to use.

**Fix (primary)**: replace the worked-example's acceptance_command with a single-executable form. Tier 3.7 runs with `cwd=scaffold_root`, so cwd-relative paths work without `cd`:

```diff
-  - Acceptance Command: cd /tmp/scaffold && .venv/bin/python -m pytest tests/test_export.py
+  - Acceptance Command: .venv/bin/python -m pytest tests/test_export.py
```
